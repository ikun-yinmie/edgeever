# 项目优化建议

> 状态：建议稿，不代表已经排期或实现
>
> 评估基线：2026-11-04，EdgeEver `1.103.10`
>
> 英文版：[Project Optimization Recommendations](project-optimization-recommendations.md)

## 1. 目的与原则

EdgeEver 已经从单一 Web 笔记应用发展为覆盖 Web、桌面、Android、iOS、浏览器扩展、Cloudflare 与 Docker 的多运行时产品。当前优化重点不应继续以增加功能数量为主，而应优先保护用户数据、统一跨端行为并降低长期维护成本。

建议遵循以下原则：

1. **用户数据正确性优先于交互便利**：任何自动覆盖、自动合并或冲突恢复都必须有可验证的产品契约。
2. **先建立契约与测试，再调整同步实现**：不得在没有跨端回归矩阵的情况下分别修改 Android、iOS、Web 或桌面端策略。
3. **Cloudflare 与 Docker 共用业务语义**：只允许基础设施适配差异，不允许认证、保存、同步或权限逻辑分叉。
4. **兼容升级优先于局部简化**：认证、数据存储、迁移、安装器和自动升级变更必须验证真实旧版本到新版本链路。
5. **优化必须可度量**：每项工作都应定义失败场景、验收标准、回滚方式与未验证项，不能以“完成重构”作为验收结论。

## 3. 优化优先级

### P0：数据正确性与产品身份

#### 3.1 将笔记更新改为数据库级原子 Compare-And-Swap

**现状**

普通笔记保存会先读取并检查 `revision` / `content_hash`，但 `apps/api/src/memo-service.ts` 中最终更新 `memo_contents` 的 SQL 只以 `memo_id` 为条件。两个并发请求可能同时通过前置检查，之后由后写入者覆盖前写入者。

**建议**

- 在 SQLite 与 D1 都支持的事务边界内实现原子 Compare-And-Swap，更新条件至少包含预期 revision 与内容 hash，或采用具有同等原子性的机制。
- 必须检查实际受影响行数；CAS 未命中时返回明确的 `revision_conflict`，不得继续写搜索投影、历史、审计或同步日志。
- 普通保存、实时协作 materialize、导入恢复和 Agent 写入必须共享同一并发语义。
- 不得只扩大 JavaScript 临界区或增加进程内锁；Cloudflare 与多进程部署不能依赖单进程内存锁保证正确性。

**验收标准**

- 两个请求基于同一 revision 并发保存时，最多一个成功，另一个稳定返回冲突。
- 正文、revision、搜索投影、历史、审计和同步日志不会出现部分提交。
- SQLite 与 D1 适配器运行同一组并发契约测试。
- 旧客户端收到冲突时仍能保留本地版本，并可显式复制或重试。

**风险与回滚**

这是数据保存核心链路的高风险变更。回滚应恢复旧代码但保留新增测试；上线前必须用旧版本客户端对新服务端执行保存和冲突测试。

#### 3.2 统一 Web、桌面、Android 与 iOS 的冲突策略

**现状**

Android 在离线草稿基线过期时进入 `revision_conflict`；iOS 当前默认允许基于最新服务端 edit session 重新提交本地正文，形成“本地正文获胜”的行为。桌面端和 Web 又有各自的冲突分类与恢复路径。

**建议**

先形成一份跨端同步契约，再修改代码。契约至少应回答：

- 同一笔记在设备 A、B 离线编辑后按不同顺序联网，最终如何处理？
- 标题、标签、正文、笔记本移动和删除是否采用相同策略？
- 哪些场景允许自动重放，哪些必须停在冲突状态？
- 是否保留两份正文，以及用户从哪里恢复未采用的版本？
- 服务端已删除、账号切换、实例重建和 sync identity 变化时如何处理？

默认建议：**不得静默以任一端正文覆盖另一端正文**。无法确定安全合并时应保留本地草稿、拉取服务端版本并进入可恢复的显式冲突状态。

**验收标准**

- 同一组 fixture 在 TypeScript、Rust 与 Swift 同步实现中得到一致分类。
- Android、iOS、Web 和桌面端对关键冲突场景显示一致结果与可恢复动作。
- 进程崩溃、重复请求和网络超时后重试不会重复创建笔记或丢失附件引用。
- 产品文档明确描述冲突行为，不使用“绝不会丢失”之类未经完整验证的保证。

#### 3.3 统一永久二开分支的文档、镜像和升级身份

**现状**

`AGENTS.md` 明确规定本仓库是永久二开分支，禁止整树同步上游；但 README 仍包含自动同步上游的部署引导，根 `compose.yaml` 默认仍指向上游官方镜像。这可能让用户部署到不同产品，或在同步上游时覆盖二开功能。

**建议**

- 明确本仓库的 canonical repository、GHCR 镜像、升级来源和故障回滚路径。
- 删除或改写会触发上游整树覆盖的用户说明。
- 检查 README、Compose、安装脚本、Release 文档、官网和 GitHub Actions 中的仓库/镜像引用。
- 保留必要的上游致谢和手工参考方式，但必须与自动升级入口严格区分。

**验收标准**

- 按公开文档全新部署时，实际运行镜像 revision 对应本仓库提交。
- 自动升级不会调用 Sync Fork 或合并 `upstream/main`。
- 文档中不存在互相冲突的推送、升级或镜像来源说明。
- 从当前正式版本升级后，注册、后台管理、邀请码和定制迁移仍然存在。

### P1：同步契约、可维护性与可复现构建

#### 3.4 建立跨语言同步协议一致性测试

TypeScript shared 包可以复用 Web 与 Android 逻辑，但不能自动约束 Rust sidecar 和 Swift 实现。建议建立与语言无关的 JSON fixture，覆盖：

- bootstrap、分页和 cursor 推进；
- 临时 ID 到服务端 ID 的映射；
- 重复提交、超时后重试和幂等；
- update/delete/restore 与待提交 outbox 的交错；
- sync identity 重置和账号/实例切换；
- revision 冲突与错误分类；
- 资源上传完成前后的笔记同步；
- 旧客户端缺少新字段时的向前兼容。

每个客户端读取同一 fixture 并输出标准化结果。协议变更必须先更新 fixture 和兼容说明，再修改各端实现。

#### 3.5 拆分大型状态编排模块

当前多个文件同时承担界面、持久化、同步、插件和编辑器生命周期协调，已经成为高回归风险区域，例如：

- `apps/web/src/components/EditorPane.tsx`
- `apps/web/src/components/WorkspaceApp.tsx`
- `apps/web/src/components/DiagramEditorPane.tsx`
- `apps/mobile/src/components/LocalTiptapEditor.tsx`
- `apps/desktop/src/main/index.mjs`

拆分目标不是单纯减少行数，而是形成可测试边界：

1. 纯内容转换与冲突决策不得依赖 React 或 Electron。
2. Repository 只负责数据访问，不负责 UI 选择状态。
3. Sync engine 负责状态机和重试，不直接弹对话框。
4. UI 只订阅明确状态并发出用户意图。
5. Electron main 中窗口、sidecar、更新、协议和系统集成功能应有独立生命周期模块。

**验收标准**

- 抽出的模块能通过无浏览器、无 Electron 的单元测试验证。
- 同步状态转换有显式状态图或 reducer，不依赖分散布尔值组合。
- 重构前后的外部行为由已有测试和新增回归测试锁定。

#### 3.6 收紧运行时与依赖版本

根 `package.json` 已声明 Bun 版本，但多个核心依赖使用 `latest`。锁文件可以固定当前安装，却会让下一次更新锁文件同时引入多个不可预测升级。

建议：

- CI 在开始构建时校验 Bun 版本，并使用 frozen lockfile。
- React、Hono、TanStack Query、Zod、Vite、TypeScript 等核心依赖使用明确版本或受控 semver 范围。
- 依赖升级按编辑器、前端框架、后端运行时、移动端和发布工具分批进行。
- 每批升级单独记录兼容性风险，禁止在功能发布中顺带大范围刷新锁文件。
- 对 patched dependency 保留“为何需要 patch、何时可移除”的回归测试或说明。

#### 3.7 扩展发布前验证矩阵

根测试已经覆盖大量纯逻辑与集成场景，但正式质量结论还需要运行时验证：

- Playwright E2E 使用一次性本地数据库，不得复用个人开发数据库。
- Docker 至少验证全新部署、持久化重启、旧版本升级和优雅关停。
- 桌面端验证 sidecar 崩溃恢复、离线写入、更新前同步和跨版本启动。
- Android 必须使用 USB 真机；不能以模拟器替代。
- iOS 验证离线 outbox、后台恢复和旧 EditorBundle 兼容。
- Cloudflare 验证 D1 migration、R2 附件和 Worker 限制下的大文件/流式路径。

### P2：性能、运维与信任边界

#### 3.8 为 Web 首屏预算保留安全余量

当前首屏 module preload 已使用预算的约 98.1%。大型图表、CodeMirror、X6 和 Mermaid chunk 已正确延迟加载，但继续向公共入口增加依赖很容易超过预算。

建议：

- 在 100% 硬失败线之外增加 90% 警告线。
- 输出导致首屏增长最大的 chunk 差异，而不仅是总字节数。
- 处理同时被静态和动态导入的模块，确保预期拆包实际生效。
- 仅对确实按需加载的大 chunk 建立 allowlist；新增例外必须附用户场景和加载时机。
- 在低性能设备上记录启动、打开大笔记、切换笔记和首次加载编辑器的基线。

#### 3.9 增强同步可观测性与用户自救能力

建议把已经存在的内部状态转化为用户可理解的诊断信息：

- 当前 sync identity、cursor 和最近成功同步时间；
- pending/syncing/conflict/error 数量；
- 最后一次错误的分类、时间与可重试性；
- 本地数据库与资源缓存位置、占用和健康状态；
- 可脱敏导出的诊断包；
- “立即重试”“复制本地版本”“拉取服务端版本”和“重建本地镜像”等分级恢复动作。

破坏性恢复必须先备份本地草稿/outbox，且不能把“清除本地数据”作为默认故障处理方式。

#### 3.10 明确隐私与扩展信任边界

自托管不等于端到端加密，插件 permission 声明也不等于强制 JavaScript 沙箱。建议在产品和开发文档中明确：

- 实例 owner 在何种策略下可以读取成员笔记；
- AI 直连或代理模式会把哪些内容发送给外部提供商；
- 客户端插件属于 trusted code，当前能访问哪些宿主能力；
- MCP Token 的 scope、撤销和审计边界；
- 日志、诊断包和 URL 中不得持久化会话或协同访问 token。

若未来引入不受信任插件，应单独设计 iframe/worker/独立进程隔离与强制 capability enforcement，不能只扩展 manifest 字段。

## 4. 推荐实施顺序

### 阶段 A：建立契约与防回归基线

1. 写出统一冲突策略和客户端能力矩阵。
2. 增加数据库级并发保存复现测试。
3. 建立跨语言同步 fixture。
4. 修正文档、Compose 与升级身份冲突。

### 阶段 B：修复数据正确性

1. 实现数据库级 CAS。
2. 统一各端冲突处理。
3. 验证旧客户端、实时协作写回和 Agent 写入。
4. 在一次性环境执行真实旧版本到新版本升级。

### 阶段 C：降低维护成本

1. 按状态机、Repository 和 UI 边界拆分大型模块。
2. 收紧 Bun 与核心依赖版本。
3. 将 E2E、Docker 和客户端验证结果纳入 Release 门禁。

### 阶段 D：性能与体验治理

1. 恢复首屏性能预算余量。
2. 完善同步诊断和用户自救入口。
3. 持续验证大数据量、长笔记、大附件和弱网场景。

## 5. 每项优化的最低交付模板

后续 Issue 或实现方案至少应包含：

1. **用户价值**：解决哪个可观察问题。
2. **影响范围**：涉及哪些运行时、客户端、迁移和发布资产。
3. **失败场景**：具体输入或状态如何产生错误结果。
4. **最坏后果**：是否可能丢数据、泄漏内容、阻断升级或导致实例不可用。
5. **兼容策略**：旧客户端、旧数据库和回滚后的行为。
6. **验证矩阵**：自动测试、真实平台和跨版本测试。
7. **回滚方案**：代码、配置、migration 和数据分别如何处理。
8. **未验证项**：明确哪些结论仍是推断。

## 6. 非目标

本建议不主张：

- 为追求“架构先进”改造成微服务；
- 在没有明确团队规模和 SQL 方言方案时立即迁移 PostgreSQL；
- 用一次大重构同时替换编辑器、同步协议和本地数据库；
- 为减少文件行数而机械拆文件；
- 在缺少容量测试时承诺百万级数据 SLA；
- 用增加自动重试掩盖非幂等、并发覆盖或数据损坏。

当前最有价值的方向是保持现有模块化单体和开放数据优势，同时把同步、并发与升级行为收敛成可测试、跨端一致的产品契约。
